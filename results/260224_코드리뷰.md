## 3. 코드 품질 분석

### 3.1 🔴 심각한 이슈 (Critical)

#### 3.1.1 파일 크기 과대
| 파일 | 줄 수 | 바이트 |
|------|-------|--------|
| `api_server.py` | 4,194 | 182KB |
| `handler.py` | 3,986 | 184KB |
| `llm_inference.py` | 3,108 | 140KB |
| `cli.py` | 1,936 | 85KB |
| `constrained_logits_processor.py` | - | 114KB |

- **문제**: 단일 파일이 3,000~4,000줄 이상으로 과도하게 비대합니다. 유지보수, 코드 리뷰, 테스트 모두 어려워집니다.
- **권장**: 각 파일을 기능별 모듈로 분리(예: `api_server.py` → `api/routes.py`, `api/models.py`, `api/auth.py`, `api/download.py` 등)

#### 3.1.2 코드 중복
- `_parse_description_hints()` 함수가 **`api_server.py`**(L505~573)와 **`cli.py`**(L93~141)에 **완전히 동일하게 중복** 되어 있습니다.
- `hashColor()` 함수가 `SongListItem.tsx`와 `RightDetails.tsx`에 중복됩니다.
- `formatDuration()` 함수도 위 두 컴포넌트에서 중복됩니다.
- **권장**: 공통 유틸리티 모듈로 추출하여 재사용

### 3.2 🟡 주요 이슈 (Major)

#### 3.2.1 보안 관련
- **API Key 비교**: `api_server.py` L431~463에서 API 키를 `==` 연산자로 직접 비교합니다. 타이밍 공격(timing attack)에 취약합니다.
  ```python
  # 현재 (취약)
  if ai_token == _api_key:
  # 권장
  import hmac
  if hmac.compare_digest(ai_token, _api_key):
  ```
- **전역 변수로 API 키 관리**: `_api_key` 전역 변수 사용은 멀티스레드 환경에서 race condition 가능성이 있습니다.

#### 3.2.2 에러 핸들링
- `api_server.py`에서 `except Exception`을 광범위하게 사용하며, 여러 곳에서 에러를 조용히 무시합니다:
  ```python
  except Exception:
      pass  # 에러 무시
  ```
- `handler.py`의 `_move_module_recursive()` (L774~782)에서 `dir()` 기반 동적 속성 탐색 시 모든 예외를 무시합니다.

#### 3.2.3 타입 안전성
- `api_server.py` L664에서 Pydantic V1 스타일 `Config` 클래스를 사용합니다:
  ```python
  class Config:
      allow_population_by_field_name = True  # Pydantic V2에서 deprecated
  ```
- `types.ts`에서 `Record<string, any>` 타입이 과도하게 사용되어 타입 안전성이 약합니다.

### 3.3 🟢 경미한 이슈 (Minor)

#### 3.3.1 코드 스타일 불일치
- Python 파일들에서 `\r\n` (Windows)과 `\n` (Unix) 줄바꿈이 혼재됩니다 (예: `api_server.py`).
- Import 순서가 일관되지 않습니다 (stdlib → third-party → local 순서 미준수).

#### 3.3.2 미사용 코드
- `app.tsx` L46~48에서 `sleep` 함수가 컴포넌트 내부에 정의되어 있지만, 별도의 `sleep`이 L128에서도 다시 정의됩니다.
- `SongListItem.tsx`의 `extractStyle()` 함수는 `extractPrompt()`와 거의 동일한 로직을 수행합니다.

#### 3.3.3 하드코딩된 값
- `api_server.py`: 매직 넘버가 많습니다:
  - `RESULT_EXPIRE_SECONDS = 7 * 24 * 60 * 60` (7일)
  - `TASK_TIMEOUT_SECONDS = 3600` (1시간)
  - `JOB_STORE_MAX_AGE_SECONDS = 86400` (24시간)
- `app.tsx` L64: 폴링 타임아웃 `15 * 60_000` (15분)이 하드코딩
- `app.tsx` L159: 폴백 URL `http://127.0.0.1:8001`이 하드코딩

## 4. 프론트엔드 (React/TypeScript) 리뷰

### 4.1 긍정적 측면
- **타입 시스템**: `types.ts`에서 체계적으로 타입 정의를 관리하고 있습니다.
- **컴포넌트 구조**: `SongListItem`, `RightDetails`, `BottomPlayer` 등 컴포넌트가 단일 책임 원칙을 잘 지키고 있습니다.
- **i18n 지원**: `react-i18next`를 활용한 다국어 지원이 구현되어 있습니다.
- **Tauri 통합**: 웹/데스크톱 동시 지원을 위한 유연한 API base URL 감지 로직이 있습니다.

### 4.2 개선 필요 사항
- `app.tsx`에서 **모든 상태가 최상위 컴포넌트에 집중**되어 있습니다. 상태 관리 라이브러리(Zustand, Jotai 등) 도입을 권장합니다.
- `Routes`에서 `/home`, `/compose`, `/create`가 동일한 `MainFeed` 컴포넌트를 렌더링합니다. 불필요한 중복이므로 와일드카드 라우트로 통합 가능합니다.
- `RightDetails.tsx`에서 인라인 스타일이 과도하게 사용됩니다. CSS 클래스나 CSS Modules 활용을 권장합니다.

## 5. 백엔드 (Python/FastAPI) 리뷰

### 5.1 긍정적 측면
- **모델 자동 다운로드**: `_ensure_model_downloaded()`가 HuggingFace/ModelScope 자동 감지 및 폴백을 지원합니다.
- **GPU 메모리 관리**: `gpu_config.py`를 통한 체계적인 GPU 메모리 설정 및 제한 관리
- **LoRA 지원**: PEFT 어댑터 로드/언로드/스케일링이 잘 구현되어 있습니다.
- **디바이스 호환성**: CUDA, MPS, XPU, CPU 모두 지원하며, 폴백 로직이 견고합니다.
- **Docstring**: 주요 함수들의 문서화가 양호합니다.

### 5.2 개선 필요 사항
- **`handler.py`의 `initialize_service()`**: 400줄 이상의 거대한 메서드입니다. 모델 로드, VAE 로드, 텍스트 인코더 로드를 별도 메서드로 분리해야 합니다.
- **인메모리 큐/작업 스토어**: `_JobStore`가 인메모리로만 동작하며, 서버 재시작 시 모든 작업 상태가 소실됩니다. 프로덕션에서는 Redis/SQLite 기반 영구 저장이 필요합니다.
- **동시 실행 제한**: `workers=1` 제약으로 인한 처리량 한계가 있습니다.
